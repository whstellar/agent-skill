# book2md

把电子书（PDF / EPUB）发布到 GitHub 仓库，并可从 GitHub 下载回来。按书名分目录存放，可反复追加新书而**不覆盖**已有内容。

## 两种用法

### 方式一：单个 HTML 文件（推荐，最轻量）

直接用浏览器打开 **`book2md.html`** 即可，无需安装任何东西、无需后端。

- PDF：原样上传，不做转换
- EPUB：浏览器内解析为 Markdown（图片一并抽出）后再上传
- Token / 仓库名自动保存在本机浏览器（localStorage），下次打开还在
- 全部在本地完成，只有上传时才联网访问 GitHub API
- 支持多选与**拖拽**文件到上传区
- EPUB 转换后可点「预览」查看渲染样式，边编辑边实时刷新（配图能真显示）
- 上传后可直接跳转到 GitHub 仓库网页下载，并自动检测私有仓库给出访问提醒

> 建议用新版 Chrome / Edge（依赖浏览器原生的 `DecompressionStream` 解压能力）。

### 方式二：本地服务（Python）

适合喜欢本地服务、想用更稳的 PDF 解析的情况：

```bash
python -m venv venv
venv\Scripts\python.exe -m pip install -r requirements.txt
venv\Scripts\python.exe app.py
# 打开 http://127.0.0.1:8787
```

## 使用步骤（HTML 版）

1. 填写 **GitHub Token**（Settings → Developer settings → PAT，勾 `repo` 权限）——会记住。
2. 填写 **仓库名**（可带 `owner/`，或只写名字用你的账号）。不存在会自动创建。
3. **拖入或选择文件（可多选）—— EPUB 会自动开始转换**，转完就可以直接点「上传全部已就绪文件」。PDF 无需转换。
   - 单本手动转换：卡片上的「转换为 Markdown」仍然可用
   - 全部手动转换：「转换全部待处理」（勾选「加入文件后自动转换」可关闭）
   - 单本可在文本框里修改，点「预览」查看渲染后的样子（**配图能真显示**，见下节）
4. 「书名 / 仓库内文件夹名」可改，决定仓库里的目录结构。

> 常用流程：**选文件** → 等转换完 → **看自检提示 + 预览** → 满意了点上传全部。
> 上传前把问题看掉，比传上去再回滚省事得多。

### 上传前先在本地看效果

每本书卡片上有两个按钮：

| 按钮 | 作用 |
| --- | --- |
| **预览** | 在卡片里展开渲染结果，就地滚动查看 |
| **存成 HTML** | 导出一份**图片全部内嵌**的 HTML 文件，用浏览器打开就是全书样子 |

两个都会把配图真正显示出来。做法是把内存里的图片字节挂成 `blob:` URL（导出时转 `data:` URI）
再替换掉 markdown 里的相对路径。

> 早期版本的预览是坏的：markdown 里写的是 `images/xxx.jpg`，而预览直接把它当 `src` 用，
> 浏览器就去页面所在目录找这个文件 —— 那儿根本没有，于是整本书的配图全裂。
> 「先看看效果」看不成的根本原因就在这。

**存成 HTML 适合什么**：书长、图多、想慢慢翻；或者发给别人确认排版，对方不用装任何东西，
文件自带全部图片。

**PDF 没有这两个按钮**：PDF 原样上传，不经过 Markdown，没法本地预览。

想确认上传后的真实效果，直接在 GitHub 上点开那个 `.md` 文件即可 ——
md 里的图片是相对路径，和仓库结构一致，会正常显示。

### 界面布局

单页布局，不再是几个大卡片堆着：

```
██  仓库 + Token + 「读取仓库」      一行完成连接，带一个绿点表示状态

██  拖入区（可多选）—— 会自动开始转换

██  进度条（常驻，空闲时置灰，不再跳来跳去）

██  自检汇总：全部无问题 / 2 本有错误

██  书目列表：每本一行摘要，点开才展开详情

██  操作区：主操作蓝色实心，次要灰色描边
██  开关区（4 个勾选项集中在一行）
██  仓库书籍面板（点「管理仓库书籍」展开，可改名/删除）
██  日志（默认折叠，出错自动展开）
```

**书籍行可折叠**：默认只显一行摘要（图标 + 书名 + 大小/图数/字符数 + 状态 + 快捷上传按钮），
点整行展开才能看到文件夹名、编辑区、重转/预览/移除。
转换中的书会自动展开，完成后自动收起，但不会挤掉你手动展开的那本。

### 大文本性能

书籍正文可达数百 KB～数 MB。一开始每本书的完整 markdown 都会在 `render()` 时塞进 textarea，
导致**上传图片很快、但 markdown 相关的操作很卡**——因为图片上传根本不碰 DOM，
而每次重绘都在往 DOM 里灌十几 MB 文本。

实测（每本 586 KB markdown）：

| 书数 | 修复前单次 render | 修复后 |
| --- | --- | --- |
| 1 | 68 ms | **2 ms** |
| 5 | 364 ms | **4 ms** |
| 10 | 966 ms | **7 ms** |

批量上传时每本书会重绘两次，10 本书原来累计近 **20 秒**纯粹浪费在 DOM 上，现在基本为零。

**做法**：收起的行不再往 textarea 里灌正文，展开时才按需填入。
展开后仍然可以正常编辑、预览、修改后上传。

## 进度显示

所有任务（转换 / 上传 / 下载）**共用顶部一条进度条**，空闲时置灰。
文字会说明正在做什么、进度到哪：

```
转换中 3 / 5（历史-skill.epub）· 读取章节 2 / 24   ▓▓▓▓▓▓▓▓░░░░░░░░░░░░  52%
上传中 2 / 5（经济-skill.epub）· 上传文件 17 / 46   ▓▓▓▓▓▓▓▓▓▓░░░░░░░░  47%
全部转换完成：5 本                                  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  100%
```

进度按本数均分，百分比是真实的整体进度，不会出现"第一本 90%、第二本又从 0% 开始"的情况。
任务结束后停留约 1.4 秒再自动隐藏；出错时停留更久（4 秒）并标红，方便看清原因。

## 在 GitHub 网页上下载文件

上传完直接去 GitHub 网页取，不必依赖本页。

**下载整个仓库**
1. 打开 `https://github.com/你的用户名/仓库名`
2. 点文件列表上方的绿色 **Code** 按钮
3. 点 **Download ZIP**

**下载单个文件**
1. 进入该文件页面（如 `原理-skill/原理-skill.md`）
2. 点右上角 **Raw** 查看原始内容，浏览器 `Ctrl+S` 保存
   - 或直接把链接 `blob` 改成 `raw`：`https://github.com/owner/repo/raw/main/路径`

**⚠️ 私有仓库的关键限制**

仓库默认建成**私有**。在**其他电脑**上访问时：

- **必须先登录同一个 GitHub 账号**，否则会跳到登录页或显示 404 —— 这是"下载不了"最常见的原因
- 登录后 Code → Download ZIP 即可正常下载

想让任何电脑不登录也能直接下载？把仓库改为公开：

```
仓库 Settings → 页面最下方 Danger Zone → Change visibility → Make public
```

页面第 ③ 步会自动检测仓库可见性，若是私有会直接显示这段提醒和对应链接。

## GitHub 上什么格式最好展示？

**只有 Markdown。** 这是 GitHub 的硬性事实，不是配置问题。

| 格式 | GitHub 上的表现 |
| --- | --- |
| `.md` | ✅ 直接渲染成网页，标题/表格/图片/代码块全支持，还能被站内搜索、diff 对比 |
| `.png/.jpg` | ✅ 原生显示 |
| `.pdf` | ❌ 不渲染，只能下载后用本地阅读器打开 |
| `.epub` | ❌ 同上，纯附件 |
| `.docx/.zip` | ❌ 纯附件 |

所以本工具的设计取向是：**内容用 Markdown 展示，原件用 PDF/EPUB 作附件留存。**

### 自动生成仓库首页

每上传一本书，工具会在仓库维护三样东西：

- `README.md` —— 给人看的**书目**，打开仓库首页就能看到
- `books.json` —— 给程序看的**索引**（书名、作者、出版社、字数、封面文件名）
- `.gitattributes` —— 告诉 GitHub 哪些是资源文件（见下）

每本书的目录里另外还有一份 `书名/README.md`，是**这本书的目录页**（见下）。

首页长这样，**封面是嵌进去的真图**，扫一眼就知道是哪本书，不必点进去看文件名：

| 封面 | 名称 | 文件 | 规模 |
|:---:|---|---|---|
| `[封面图]` | **原理-skill**<br><sub>某作者 · 某出版社</sub> | [md](…) · [pdf](…) | 12.3 万字<br>156 图 |
| `[封面图]` | **book2demo**<br><sub>某作者</sub> | [md](…) · [epub](…) | 2.1 万字<br>1 图 |
| 无封面 | **fankang** | [md](…) | 12 KB<br><sub>2026-10-19</sub> |

页首汇总：`# 仓库名 / 共 N 个 · 约 X 万字 · Y 张配图`，下面一行小字 `最近更新 2026-10-20 20:34`。
**标题取的是仓库名**，不写死——这个工具不止用来放某一种东西，clone 过去首页也不会文不对题。
「规模」列最后一行也会带上这本书的 `books.json` 上传日期。

#### 有的书有封面、有的没有，是怎么回事

| 源文件 | 封面来源 |
| --- | --- |
| `.epub` | 从 EPUB 的 OPF 里取（`properties="cover-image"`，取不到再按文件名猜 `cover*`） |
| `.pdf` | **原本没有**，自动生成文字封面 |
| `.md` | **原本没有**，自动生成文字封面 |

封面提取只发生在 EPUB 解析这一步，PDF 和 MD 两条路径压根没有这个环节。
所以日志里那几本「无封面：博弈skill、纳瓦尔-skill…」，其实顶层只有 `博弈skill.pdf`、
`纳瓦尔-skill.md` —— 源文件本身就没有封面，不是渲染坏了。

现在对没有真封面的书自动生成一张 SVG 文字封面：底色按书名哈希取（同一本书永远同一个色），
书名居中、按**视觉宽度**折行（中文字算 1，拉丁/数字算 0.55，所以 `博弈skill` 不会被切成
`博弈skil` + `l`），底部标 `PDF` / `MARKDOWN` / `EPUB`。
几 KB、零依赖、GitHub 直接渲染，文件名仍是 `cover.svg`，所以 README 的扫描规则不用改。

故意做成浅色底 + 虚线框，**一看就是占位**，不冒充真封面。

已经传过的老书也不用一本本重传：点「重建首页」会先扫一遍仓库，
把所有缺 `cover.*` 的目录补齐（一次 commit，只新增 `cover.svg`，不动任何书籍文件）。

#### 每本书的目录页（`书名/README.md`）

在 GitHub 上点进 `书名/` 这个目录，默认看到的是**一列文件名**——
封面缩略图、作者、出版社、下载入口全都没有，想下原件还得先点进正文再从里面找。

现在每本书会额外生成一份 `书名/README.md`。GitHub 会自动把它渲染在目录列表下面，
于是每本书的目录页就是一张封面 + 书名作者 + 下载链接，像个正经书架，
顶部还留了回首页的入口，不用一路点浏览器后退：

```markdown
<div align="center">

# 三国演义

<img src="cover.svg" width="180" alt="三国演义">

<sub>罗贯中 · 人民文学出版社</sub>

</div>

---

正文约 68.2 万字 · 156 张配图 · 语言 zh · 上传于 2026-10-21

## 阅读与下载

- [在线阅读](三国演义.md)
- [下载 EPUB 原件](三国演义.epub)

---

[← 返回书库首页](../README.md)
```

里面的 `cover.svg`、`三国演义.md` 都是**相对这份 README 自己**的路径。
GitHub 的 Markdown 相对链接就是按当前文件所在目录解析的，所以这样写刚好对上仓库结构，
不会出现「首页能看、点进去 404」。

#### `.gitattributes`：别让语言条被资源文件带偏

随首页同一个 commit 一起写入（不额外多花一次 API 调用），解决两件只看主页就能发现的事：

| 问题 | 原因 | 处理 |
| --- | --- | --- |
| 语言条显示成「SVG 98%」，看着像个前端项目 | SVG 在 linguist 里属**文本/markup**，会被计入统计；一个仓库几十本自动生成 `cover.svg` 就把真实占比顶掉了 | `cover.svg linguist-generated` |
| 传完书 diff 刷屏，几百条二进制改动 | 图片/原件在 diff 里逐条列出 | 资源后缀一律 `binary linguist-vendored` |

覆盖的后缀：`jpg / jpeg / png / gif / webp / svg / epub / pdf / mobi / azw3 / djvu`。

开头带注释说明「由 book2md 自动维护，可改，下次重建首页会补回来」——
手写的内容不会被无脑覆盖掉，但删了会自动补。

#### 为什么 GitHub 上书的文件夹时间一直是旧的

这是**正常现象，不是没上传**。GitHub 目录列表显示的时间是「**这个目录里文件最后一次被修改**的 commit 时间」，
而「重建首页」只提交了根目录的 `README.md` 一个文件——书目录里的文件没进那个 commit，时间当然不动。

判断有没有真的写进去，看这三处任何一个：

| 看哪里 | 更新后会变成 |
|---|---|
| 仓库根目录的 `README.md` 那一行 | 刚刚 |
| 页首小字 | 你点重建的那一刻 |
| 仓库 Commits 列表 | 多一条 `update README book index` |

只想确认书有没有变，就看那本书文件夹里的 `xxx.md` 那一行——重新上传时如果内容一个字都没变，
工具会直接跳过（日志里是「N 个文件与仓库完全一致，跳过上传」），**不产生新 commit，时间也就不会变**，这是刻意的省流量行为。

#### 大坑：「已存在文件一律不覆盖」会让重传变成空操作

设置里有个勾选框 `已存在文件一律不覆盖（内容变了也不覆盖）`，它是**持久化保存**的，勾过一次就一直生效。
勾上之后，重传已上传的书时，同名文件会被无脑跳过——**哪怕你本地的内容已经变了**。

曾经的表现是这样的乌龙：改完转换逻辑 → 重传 → 日志显示「27 个文件内容未变，跳过上传」→
看着像成功 → 打开 GitHub 一看，文件夹时间还是昨天的，md 还是旧的。
而且那句「内容未变」是**假话**：勾着开关时它压根没比对内容。

现在改成了：

- 无论开关是否勾上，**都先比对内容**（本地算 blob sha，不花 API 调用）；
- 内容真的相同 → `N 个文件与仓库完全一致，跳过上传`（正常，省流量）
- 内容不同但被开关挡住 → `⚠ N 个文件内容和仓库不一样，但被「已存在文件跳过不覆盖」挡住了`，
  并列出文件名、直接告诉你「取消勾选后再传一次」；结尾还会追加一句
  `⚠ 这次上传其实没有向仓库提交任何内容，GitHub 上的时间自然不会变`
- 启动时如果发现这个开关是勾着的，日志里会先给一条醒目警告

**想更新已上传的书，这个勾必须保持不勾。**

#### 「一本更新了、一本没更新」怎么看

一次传多本时，批量结束会打一张结论表，谁动了、谁没动，一眼能分清：

```
── 本次结果 ──
  ✔ 提问-skill：提交 25 个文件，另有 2 个未变化
  ○ 另一本-skill：一个文件都没提交 —— 转换结果和仓库里已有的完全一致（含 另一本-skill.md）
  共 2 本：1 本有更新，1 本没有变化
```

- `✔` 提交了文件，GitHub 上会有新 commit，文件夹时间变成今天
- `○` **一个文件都没提交**，因为转换结果和仓库里逐字节一致。这不是失败，是没必要提交
- `⚠` 内容确实变了，但被「已存在文件一律不覆盖」挡住了（见上一节）

书籍状态标签也分开了，不再是清一色的「已上传」：

| 标签 | 含义 | 要不要处理 |
| --- | --- | --- |
| **已上传**（绿） | 文件都进仓库了 | — |
| **部分成功（N 个没传上）**（绿） | 大部分进了，但 N 个文件没进去 | 要，看日志里的 `[失败]` 行 |
| **无变化（已是最新）**（橙） | 一个文件都没提交，因为转换结果和仓库里逐字节一致 | 不用，这是正常的 |
| **被设置挡住**（橙） | 内容确实变了，但被「已存在文件一律不覆盖」拦下 | 要，取消勾选后重传 |
| **上传失败**（红） | 一个都没进去 | 要，看日志 |

**「部分成功（N 个没传上）」的三种成因**：

1. **文件内容是空的** —— EPUB 里某张图解压出来是 0 字节。这是最常见的，日志会写
   `[失败] 书名/images/xxx.jpg：内容为空`
2. 单个文件超过 90 MB（GitHub 的 blob 上限附近）
3. 某个 blob 连续重试仍失败（限流、网络）

出现这个状态时日志框会自动展开，并在末尾追加一行
`⚠ 有 N 个文件没进仓库，往上翻找 [失败] 开头的行` —— 原因都在那几行里。

`○` 为什么会出现：只有当这本书的转换结果真的变了，才会产生提交。
如果它在昨天那批 bug 修复前就已经是正常格式（没有空书名、没有全角空格丢失、没有脏图片名），
重新转换出来的结果和仓库里一模一样 —— 那就什么都不用传。要确认是"重新转换过"而不是"点列表里的旧记录"，
看日志开头有没有 `转换中` / `转换完成` 那两行。

这个 README 会在每次上传后自动重建（读取仓库真实文件列表），所以新增书籍后首页自动更新。仓库里已有的老书如果早于这次改动上传、没有 `books.json` 记录，会退化为显示文件夹名——重新上传一次即可补上真书名和作者。

只想刷新首页、不想重传书，点工具栏的 **重建首页**：它只重新扫描仓库并重写 `README.md`，一个书籍文件都不碰。
页面顶部版本条里的版本号可以用来确认自己加载的是不是最新的那份 HTML（见下方"改了没生效"）。

#### 首页写不进去：`找不到仓库或路径（检查仓库名是否正确）`

这个报错看着像仓库名填错，实际最常见的成因是**写分支引用的端点写成了单数**：

| 操作 | 正确端点 | 错误端点 |
|---|---|---|
| 读分支头 | `GET /git/ref/heads/main` | — |
| **移动分支引用** | **`PATCH /git/refs/heads/main`** | `PATCH /git/ref/head/main` ✗ |

GitHub 这两个端点一个单数一个复数，`GET` 用单数没问题，`PATCH` 用单数必 404。
更麻烦的是它会**伪装成功**：书本身有降级路径（批量提交失败就逐个文件上传），所以书照样进仓库，
只有 README 没有降级、直接报错——看起来像"书能传、首页不行"的怪毛病。

现在版本做了三件事：
1. `PATCH` 一律用复数 `refs`；
2. 取分支头改用 `GET /commits/{branch}?per_page=1`（同时接受分支名、tag、sha，比 `/git/ref/` 容错高），
   分支名对不上时重问一次仓库并自动纠正；
3. 报错信息带上真实失败的路径，例如 `← /repos/xx/yy/git/ref/heads/main`，一眼能看出是端点写错还是仓库名写错。

测试里也补了对应断言：假仓库现在**只认复数 `refs`**（单数直接 404，不再惯着），
并且会数"批量提交成功几次、退回逐文件上传几次"——防止快路径悄悄退化成慢路径还一路绿灯。之前假仓库两个都收，正好把这个 bug 一路掩盖到线上。

### 为什么 PDF 在 GitHub 上"下载不了"

两个原因叠加：

1. **GitHub 对 PDF 只提供下载**，点进 PDF 文件会显示 blob 页面而非直接下载，必须登录才能通过校验；
2. **你的仓库是私有的**，换电脑没登录同一账号 → 跳转登录页或 404。

解决：登录即可，或把仓库改为公开。若确实需要在 GitHub 内**在线预览** PDF，GitHub 原生做不到，只能靠外部 PDF.js 之类的方案，且私有仓库仍受登录限制——不如直接用 Markdown 阅读体验好。

## 公开仓库的展示优化

公共仓库（`private = false`）可以做得更好看。工具已做以下几件事：

### 1. 自动提取 EPUB 封面

> 封面只在解析 EPUB 时从 OPF 里取。**PDF 和直接上传的 `.md` 本来就不带封面** ——
> 这类书现在会自动生成一张文字封面（见下方「没有真封面的书」）。


从 OPF 里按优先级定位封面：
1. `manifest` 中 `properties="cover-image"` 的项
2. `<meta name="cover" content="...">` 指向的项
3. 兜底取第一个图片类文件

封面存为 `书名/cover.jpg`（扩展名按原图类型）。

### 2. 首页做成带封面的列表

仓库根目录的 `README.md` 自动重建为带封面的表格：每行一个条目，**左列是封面缩略图**（`<img width="76">`，直接引用 `名称/cover.jpg`），右边是名称、作者、下载链接和规模。

| 列 | 内容 | 来源 |
| --- | --- | --- |
| 封面 | 封面缩略图，无封面时显示「无封面」 | 扫描 `名称/cover.*` |
| 名称 | 书名（可点进 `.md` 在线阅读）<br>小字：作者 · 出版社 | `books.json` 里记录的 EPUB 元信息 |
| 文件 | `md` / `pdf` / `epub` 直达链接 | 仓库实际文件 |
| 规模 | 字数 + 插图数；没有字数记录时退回 `.md` 体积 | `books.json` + 目录扫描 |

页首还有一行汇总：共几个、合计多少万字、多少张配图。

路径里的中文不转义（`红楼梦/cover.png` 而不是 `%E7%BA%A2…`），源码可以直接读、也可以手改；只有空格、括号、`#` 这类真会破坏链接的字符才编码。

### 3. GitHub Pages 在线阅读站（可选）

公开仓库可免费开启 Pages，把仓库变成真正的网站：

```
Settings → Pages → Source 选 Deploy from a branch
           Branch 选 main，目录选 / (root)
```

约 1-2 分钟后访问 `https://<用户名>.github.io/<仓库名>/`。

> ⚠️ Pages 是**整站静态托管**，会把仓库里所有文件按原样暴露。所以只放打算公开的内容。

页面第 ③ 步检测到公开仓库时，会自动显示这段引导和链接。

## EPUB 可以上传并在 GitHub 下载吗？

可以，已经支持。EPUB 有两种上传方式，可按需勾选：

| 勾选 | GitHub 里保存的东西 |
| --- | --- |
| 默认（不勾） | `书名.md` + `cover.jpg` + `images/` —— 转换后的 Markdown 与封面 |
| 勾上「同时保留原文件」 | 额外存一份 `书名.epub` 原件 |

- **全局开关**：选文件区有「新建的 EPUB 默认保留原文件」，批量处理时一次设置。
- **单本开关**：每本书的卡片上也有独立复选框，可逐本调整。
- 保留原件后，在下载中心点「下载整本 (zip)」就能把 `.epub`、`.md`、图片一起打包拿回来。

## 仓库结构

每次上传后，工具会重建仓库根目录的 `README.md` 书架，并合并更新 `books.json` 书库索引：

```
<仓库根>/
  README.md                 ← 自动生成的书架索引（打开仓库首页即见）
  books.json                ← 书库元信息：书名/作者/出版社/字数/封面文件名
  .gitattributes            ← 标记资源文件：不进语言统计、diff 里折叠
  原理-skill/
    README.md               ← 这本书的目录页（点进目录时 GitHub 自动渲染）
    原理-skill.md           ← Markdown 内容，GitHub 原生渲染，可直接阅读
    cover.jpg               ← 从 EPUB 自动提取的封面（没有则生成 cover.svg）
    images/                 ← 插图
    原理-skill.pdf          ← 原始 PDF 附件（可选）
    原理-skill.epub         ← 原始 EPUB 附件（可选）
```

`books.json` 只维护「本次上传的那一条」，其他书的条目原样保留；万一它被删掉或损坏，README 仍能正常生成，只是书名退化为文件夹名。想手动改书名、作者，直接编辑 `books.json` 再点一次上传任意一本（或重新上传那本书）即可重排。

同名路径默认**覆盖更新**（带 sha 走 GitHub 更新接口，改动能生效）；勾选「已存在的同名文件跳过不覆盖」则保留原文件。README 索引每次重新生成，保证与实际文件一致。

## 稳定性与安全

经过一轮实测审查，修复了以下问题：

**数据丢失类**
- 编辑中的 Markdown 会被其他操作触发的界面重绘抹掉 → 现在实时同步回内存，改动不再丢失
- 全部文件上传失败时仍显示「已上传」→ 现在区分「已上传 / 部分成功 / 上传失败」
- 文件名含裸 `%`（如 `50%off.xhtml`）会让整本 EPUB 崩溃 → 加了容错解码

**覆盖与更新**
- 已存在的文件只能跳过、无法更新 → 改为带 sha 走更新接口，改动能生效
- 上传前预检体积，超过 GitHub 单文件 100MB 上限时本地拦截并给出可读原因
- 目录名做路径净化，`../` 路径穿越与非法字符被拦截

**图片裂图（GitHub 上显示不出来）**

- EPUB 里的图片名常带空格 / 括号 / 井号 / 问号 / 百分号（`my photo 1.jpg`、`figure(2).png`、`a#b.png`）。这些字符在 Markdown 链接里都是语法的一部分：空格截断目标、括号提前闭合、`#` 变锚点、`%` 被二次转义 —— 于是本地看着好好的，到 GitHub 上就是一片裂图。
  现在文件名统一净化（特殊字符转下划线，中文保留），输出路径再兜底转义。
- `../Images/UP.JPG` 和 `../images/up.jpg` 指向同一张图时被当成两张：其中一张能填内容、另一张永远为空。路径现在按大小写归一，一张图只提交一份。
- OPF 里 `href` 允许带 `#fragment`（指向 SVG 内部元素），截断处理会误伤 `a#b.png` 这类文件名，导致它从 manifest 里消失。改为先查 zip 里有没有完整路径，再决定是否截断。
- 封面链接原本写成 `[封面](dir/cover)`，漏了扩展名，是条死链。

**格式**

- **每本书的书名都是空的**：OPF 用 Dublin Core 命名空间（`<dc:title>`），而 `getElementsByTagName('title')` 在 XML 文档里按 qualifiedName 匹配，`dc:title` 的 qualifiedName 是 `dc:title`，一个都取不到 —— 每篇开头都是一个光秃秃的 `# `。改为按 localName 匹配。
- 书名那个 H1 参与了标题层级归一化，把整本书的标题整体压低一级（书名 H1→H2、章节 h2→H3）。改为只对正文归一化，再拼书名。
- `第一章　绪论` 里的全角空格被压成半角、再被"中文之间不留空格"的规则吃掉，标题粘成 `第一章绪论`。用占位符保护后再还原。
- 表格按**表头**列数截断，某行多出来的单元格直接丢掉（数据无声消失）。改为按整张表最宽的一行补齐，表头分隔行也同步。
- 列表项内部的空行让整项被包进 `<p>`，GFM 渲染成"松散列表"（每项之间一大段空隙）。只压掉紧挨列表标记的空行。
- 表格自检把整篇所有表格行放在一起比列数，两张列数不同的表就误报"列数不一致"。改为按连续行分块，逐张检查。
- **正文里露出 `**`、或者整段莫名变成斜体**：根子是强调标记没配上。四种来源：
  ① 单个 `*` 没闭合 —— 而自检以前**只扫 `**`，单星号是盲区**，一条都不报；
  ② 转换时给内层已经带 `*` 的内容又套了一层标记，拼出 `*abc**` 这种数不对的串；
  ③ 标记内容首尾带空格（`*abc *`、`**绝对优 **`、`**　绝对优**`），CommonMark 里**不算闭合**，
  星号原样露出、后面整段还可能被吞成斜体；
  ④ `<b>` 标签内层换行缩进（`<b>\n  绝对优</b>`），内层文本天然以空格开头 —— 电子书里最普遍的一类。
  四处都修了，并新增 `scanItalic()` 扫单星号、`scanBold()` 改为按"能否开/能否闭"配对
  （跳过乘号 `5*3`、变量 `a*b`、代码、转义、分隔线、以及原文里的字面星号）。
  同时**把本地预览改得和 GitHub 一样严格** —— 以前预览认这些写法照样加粗，
  于是出现"本地好好的、上传后全是星号"，用户根本没法在本地自查。
- **自检报「标题跳级：H2 之后直接是 H4」**：层级映射用的是"出现过哪些级别"，只能防撞车、防不了断层。
  只要书里有个异常级别（比如拿 `h6` 当小标题）插在中间，正常级别就被顶去更深一档。
  改为父级栈推导深度 —— 相邻两级最多差 1，结构上不可能再跳级（详见下方"标题层级归一化"）。

**安全**
- 预览区过滤 `javascript:` 等危险协议 —— EPUB 来自外部文件，而本页把 PAT 存在 localStorage，一旦点中被点链接等于泄露 Token
- 链接统一加 `rel="noopener noreferrer"`

**转换正确性**
- 代码块（``` 围栏）内的 `# 注释`、缩进、空行不再被清理逻辑改坏
- 块级容器的 `font-weight:bold` 样式不再把多段内容整体包进 `**`（会导致加粗跨段落失效）

**请求效率**
- 复用仓库信息与整树 sha，避免每个文件多一次探测请求（单本 13 次 → 9 次）
- 整树接口被截断时降级为逐文件校验，不再静默吞掉限流/权限错误

**上传健壮性**

上传默认使用 **Git Data API 批量提交**：整本书的所有文件合并成 **1 个 commit**。

```
POST /git/blobs     每个文件一个（内容寻址，GitHub 自动去重相同内容的 blob）
POST /git/trees     一次，带 base_tree 保留仓库里其他书
POST /git/commits   一次
PATCH /git/refs     一次，把分支指到新 commit
```

对比之前逐文件走 Contents API：

| | 逐文件 | 批量提交 |
| --- | --- | --- |
| 一本 300 图的书产生 commit 数 | 301 | **1** |
| 一次书籍上传更新分支次数 | 301（每文件一次） | **1** |
| 书内 ref 竞态风险 | 高 | **零**（中途不动 ref） |
| 请求总数 | ~301 | ~303（+2，但少 300 个 commit） |

请求数基本持平，但**分支只在最后动一次**，所以一本书内部根本不可能撞上 `is at X but expected Y`；
仓库历史也干净，不会被几百条 "add image_xxx" 刷屏。

补充保障：
- **所有会移动分支的操作串行化**：`commitFilesBatch`（提交书籍）、`updateReadme`（更新索引）、
  逐文件降级路径，统一经一个队列排队，任意时刻只有一个请求在改分支指针。
  上传期间点其他书的「上传此文件」会被拦下并提示等待。
- **分支头在锁内现取**：这是关键。批量提交要先花几分钟建 blob，如果分支头在锁外读一次就开工，
  等建完 blob 那个 sha 早就过期了（README 更新等操作已把分支推走），最后 PATCH 必然报
  `is at <sha> but expected <sha>`。所以「读 ref → 建 tree → 建 commit → PATCH ref」
  整个过程必须在锁内一次做完。README 更新同理，且改用 Git Data API 而非 Contents API，
  不再依赖调用方传进来的（可能已过期的）sha。
- **自动降级**：批量提交若失败，自动回退到逐文件上传，保证内容能传上去。
- **竞态错误纳入重试**：分支冲突按退避策略重试（最多 4 次）。
- **单文件失败不影响整本**：某个 blob 建失败只跳过它，其余照常进 tree。
- **报错翻译成人话**：`401 Bad credentials` → `Token 无效或已过期`，
  `is at xxx but expected yyy` → `分支写入冲突（多本书同时上传导致）`。
- 想手动切回逐文件模式？取消勾选「整本书合并为 1 个提交」即可。

> **这个错误是什么**：`is at A but expected B` 是 Git 的引用竞态（ref race）。
> 意思是"我基于 B 构建新提交，但分支现在已经指向 A 了，我不能凭空覆盖"。
> 几乎总是因为**两个写操作同时基于同一个父提交**。只要所有移动分支的操作串行化，就能根治。

## 转换质量：统一规范化

为让不同来源的书转换后**排版一致**，做了这些处理：

### 字号与字重统一（避免"有的粗有的不粗、字大字小"）

电子书里的字号和加粗大多是**排版需要**，不是语义强调。转换时按以下规则归一化：

| 原书情况 | 处理结果 |
| --- | --- |
| `<span style="font-size:90%">` 压小塞字 | **剥离字号**，按正文输出 |
| 整段 / 块级容器加粗（`.bold{font-weight:bold}`） | **剥离加粗**，只留文字 |
| 加粗文本超过 8 字 | 视为排版，**剥离** |
| 加粗文本含句读（`，` `。` 等） | 视为排版，**剥离** |
| `<strong>重点</strong>` 这类短促强调 | **保留粗体** |
| `<em>` / `font-style:italic` | **保留斜体** |

判断依据包括 **computed style**，因此 `<style>` 里写的 CSS 类（如 `.txt{font-size:90%}`）也能被识别，而不是只认内联 `style=`。

### 标题层级归一化

不按原始 `h1~h6` 的绝对值下移（那会产出 `####` 这种过深层级），而是**用父级栈推导深度**：
遇到一个标题，先把它后面所有"不比它浅"的祖先弹出栈，剩下的祖先数量 +1 就是它的深度。
H1 留给书名，所以正文从 H2 起。

```
## 第一章          ← 章（一档）
### 一、某某小节     ← 小节（二档）
```

不同书用 h1 还是 h3 表示章节都不影响，最终统一为 H2/H3/H4。代码围栏（``` ）内的 `#` 注释不会被误当标题。

#### 为什么不能用"出现过的级别列表"做映射

早期版本收集文档里出现过的所有级别，按出现顺序映射成 H2/H3/H4…。这只能保证**不同级别不撞车**，
保证不了**连续**，于是自检会报：

> `[提醒] 标题跳级：第 289 行 H2 之后，第 349 行直接是 H4（故事引申）`

两种典型触发：

| 书里的脏结构 | 映射法的结果 | 栈算法 |
| --- | --- | --- |
| 章 `h2` 下面直接 `h4`（作者跳过 h3） | H2 → H4，跳级 | H2 → H3 ✓ |
| 拿 `h6` 当小标题，且出现在 h2 与 h4 之间 | `h4` 被推到更深一档，照样跳级 | H2 → H3 → H3 ✓ |

栈算法每次都只比"比我深的祖先出栈"，所以相邻两级的深度**最多只差 1，结构上不可能跳级**。
代价是 `h6` 和紧跟着的 `h4` 可能并成同一档 —— 但它们本来就是兄弟关系（h4 弹出 h6），
并档比凭空造一个断层好。

这条性质由 `check_markdown.js` 里的单元测试锁住（4 种脏结构：章下直接 h4 / h6 夹中间 / 正常三级 / 六级全用），
与具体哪本书无关，每次跑测试都会先验一遍。

### 强调标记：为什么正文会露出 `**`

`**降低不平等的斯堪的纳维亚模**式`、`**绝对优**势`、`**循证经济学习题**` 这种看着像渲染坏了的东西，
其实都是**标记没配上**。自检现在会直接报出来（带行号和那一行的原文）：

> `[错误] 第 289 行的 ** 在 GitHub 上不会生效，星号会原样印进正文（CommonMark 规定标记内侧不能贴空格、且必须成对）。去那一行把星号内侧的空格删掉：…`

**最关键的一条：标记内侧不能有空白。** `**绝对优 **`、`** 绝对优**`、`**　绝对优**`（全角空格）
在 CommonMark 里**都不算闭合**，星号会原样印出来。而电子书里 `<b>` 内层带空白几乎躲不掉：

```html
<strong>
    循证经济学习题
</strong>          →  内层文本 = "\n    循证经济学习题\n  "  →  ** 循证经济学习题 **
<strong>绝对优 </strong>势                              →  **绝对优 **势
<strong> 绝对优</strong>势                              →  ** 绝对优**势
```

更麻烦的是**本地看不出来**：页面里的正则预览认这些写法（照样加粗），GitHub 不认。
于是"本地看着好好的、上传后全是星号"。所以这一版在三个地方同时改：

| 位置 | 改动 | 说明 |
| --- | --- | --- |
| 生成侧 | 新增 `wrapMark()` | 所有 `**` `*` `~~` 统一走它：先 `trim()` 再包标记，空白留在标记外面 |
| 兜底层 | 新增 `fixEmphasisSpacing()` | 挂进 `cleanupMd`，把**原文自带的** `**a **` 自动改成 `**a** ` |
| 预览侧 | `renderMdPreview` 变严格 | 标记内侧贴空白就不加粗 —— 本地看到什么，GitHub 就是什么 |
| 自检侧 | `scanBold` / `scanItalic` 重写 | 按"能否开/能否闭"配对，报"开了没闭上"的那个 |

四个来源，现在都在转换侧堵住了：

| 来源 | 表现 | 处理 |
| --- | --- | --- |
| 单个 `*` 没闭合 | 后面一大段都变斜体，`*` 露出来 | `scanItalic()` 报错并定位到行 |
| 内层已带 `*` 又套一层 | 拼出 `*abc**`，星号数量错乱 | `wrapMark()` 内层含 `*` 时不再套外层 |
| 标记内侧带空格（半角/全角） | `**绝对优 **` 星号原样露出 | `wrapMark()` + `fixEmphasisSpacing()` 双保险 |
| 标签内换行缩进 | 内层文本以空格开头，同上 | 同上 |

**扫描器的难点一直是「不误报」**，所以刻意放行了这些：乘号 `5*3`、变量 `a*b`、
代码块与行内代码里的星号、转义 `\*`、粗斜体 `***…***`、分隔线 `* * *`、
以及**原文里本来就写的字面星号**（"直接写 `**` 而不加空格"、"`x  **2`"这种公式）。
最后一条是被真实书稿打回来的：第一版扫描器把字面星号全报成错误，一本书刷出十几条红字。

这些都锁在 `check_markdown.js` 里了：
- wrapMark 6 例（半角/全角/纯空白/内层带星）
- 60 种脏写法过一遍 `cleanupMd`，用**真解析器**（commonmark）验证不再露星
- 漏报 7 例（`** 绝对优**` 这类必须报）、误报 11 例（字面星号必须不报）
- 预览对齐 4 例（预览和 GitHub 的加粗结论必须一致）
- 行号定位 1 例（报错行号曾经永远指向第 1 行 = 书名）
- 端到端样本 `samples/em_space.epub`（标签内换行缩进、全角空格、嵌套强调、逐字加粗姓名、字面星号）

**逐字加粗的姓名会拼出四个星号连排**：`<b>徐</b><b>浩</b><b>庆</b>` → `**徐****浩****庆**`。
字间距排版的书里作者名常这么写。cmark 其实能渲染（只是套了一层多余的 `<strong>`），
但四个星号挤在一起容易被别的解析器判错，自检也会误报。现在两头都处理：

- 生成侧 `joinInline()` 里加了 `mergeSeam()`：相邻两段是同一种标记时把接缝抹平 → `**徐浩庆**`
- 兜底侧 `fixEmphasisSpacing()` 用循环把历史 md 里的 `****` 接缝合并掉

同一处还修了一个连带 bug：这两个正则原本会在**行内代码**上动手，
把书里 `` `**徐****浩****庆**` `` 这种示范字符串改坏。现在统一走 `mapOutsideCode()`，
反引号跨度里的内容一个字都不动。


### 性能与界面：只有"用久了 / 书大了 / 书多了"才暴露的问题

这几条都不是功能错误，功能看起来一直是好的，所以长期没人发现。**现在有 `ui_check.js` 专门盯它们**（17 条断言）。

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 大书在编辑框里打字卡 | 每敲一键都跑 `bytesToBase64(整篇)` + 全量重渲染预览。实测 1MB 正文：15ms + 76ms/键，浏览器还要 innerHTML 与几百张图重排 | base64 改成"上传时才算"（输入时只置空）；预览与自检共用 400ms 防抖。同样的书实测降到 **1.45ms/键** |
| 打字打到一半光标跳走 | 自检结果一变就 `render()`，而 render 会 `innerHTML=''` 重建整行 —— 正在输入的 textarea 被销毁重建 | 新增 `refreshRow(i)`：只就地替换状态徽章与自检面板，绝不碰输入框 |
| 换几本书之后内存只涨不降 | 预览用的 `URL.createObjectURL` 只有造、没有放 | 新增 `releaseImgUrls()`：重新转换、移除书籍、清空列表时逐个 revoke |
| 转大书时进度条不动、页面像卡死 | 解析整章是纯同步 DOM 活，循环里没有宏任务让出，浏览器没机会重绘 | 新增 `paint()`（内部节流 100ms，避免让出太勤把转换拖慢），每 5 章/5 图让一帧 |
| 两本书传同一个文件夹，最后只剩一本 | 文件夹名是手填的，撞车没有任何提示；后传的静默覆盖先传的，不报错也不失败 | `dupFolders()` + `refreshFolderWarnings()`：撞名的输入框标红、列表顶上给提示；上传前 `blockIfDupFolder()` 直接拦下并说明怎么改 |

`ui_check.js` 里最要紧的一条是"自检结果变了之后，编辑框还是**同一个元素**"——
它锁住的正是"打字被打断"这件事；只要有人图省事改回 `render()`，测试立刻红。

### 资源：别把仓库当垃圾桶

| 现象 | 实测 | 处理 |
| --- | --- | --- |
| 同一张装饰图被传几十次 | 真实书《现代》4827 张图里 **71 张内容完全相同**，`image_000.png` 一个文件出现 26 次 —— 就是往仓库传 26 个一模一样的文件 | 按 sha1（复用 `gitBlobSha1`）归并：重复的名字从图片表里删掉，正文里的引用统一改指向保留的那一份。新增样本 `samples/dup_img.epub` 端到端验证（3 张相同 + 1 张不同 → 只剩 2 张，5 处引用全部改指向） |
| 没勾「保留原件」也白算一份 base64 | 实测 20MB → **157ms + 常驻 53MB**（base64 在 JS 里按 UTF-16 存，是原体积的 2.6 倍）；90MB 的书约 700ms + 约 240MB，而默认根本不会上传它 | 新增 `ensureOrigB64()`：上传时才懒算，不勾就一分内存都不占；顺手去掉 `new Uint8Array(buf)` 那次多余的整文件复制 |
| 勾了「保留原件」却不生效 | 原来只在加书那一刻读一次勾选框，之后再改对已添加的书完全无效 | 勾选框 change 时同步到所有已添加的书，并在日志里说明生效范围 |

### 其他处理



**噪声剔除（只删装饰，不删正文）**
- 页眉页脚：`page-header` / `page-footer` / `running-head` 等类名，按**完整 class 名精确匹配**
  —— 早期用子串匹配，`bookmark` 会把 `<div class="bookmark-list">` 里的正文整段删掉
- 导航标记：`epub:type` 为 `noteref` / `biblioref` / `pagebreak` / `toc` 的节点
- **脚注/尾注保留**：`epub:type="footnote"` / `endnote` 是注释正文，属实质内容，不删除

**文本与空格**
- 软换行合并：段落内 `<br/>` 视为空格
- 中文空格统一：中文语境的源码换行与缩进**直接丢弃**，西文语境才保留单空格
- 汉字之间的普通空格也会去掉，`&nbsp;` 同样处理 —— 这是"文字 有 的 大 小"的另一个来源
- Markdown 标记边界：判断是否补空格前先剥掉 `**` `*`，避免 `**重点**后面` 出现多余空格

**结构保真**
- 表格：首行即表头（不再往后找含 `th` 的行，否则数据行的 `th` 会被误升为表头）；
  列数以表头为准，多的截断、少的补齐
- 嵌套列表：续行缩进按列表标记宽度计算（有序表 `1. ` 需 3 空格以上），否则 GitHub 会渲染成同级
- 上下标：`<sub>` / `<sup>` 转成 HTML 内联标签，`H<sub>2</sub>O` 不会被拉平成 `H 2 O`
- ruby 注音：`<ruby>漢<rt>かん</rt></ruby>` → `漢（かん）`
- 行内代码：内容含反引号时改用更长的反引号包裹（`` ``a`b`` ``），因为 CommonMark 不支持反斜杠转义
- **代码块留在原位**：清洗（空行压缩、行尾去空白）时整块换成单行占位符，洗完再回填。
  早期把围栏块抽出来**追加到文末**，于是第 2 章的示例代码跑到了全书最后
- 代码块围栏自动加长：围栏长度 = `max(3, 内容里最长反引号段 + 1)`。
  固定三个反引号时，示例里出现 ` ```python ` 会被当成结束标记，
  状态从那一行起**全反**——后半本书的代码和正文会整个错位
- 代码语言标注：从 `language-` / `lang-` / `highlight-` 类名提取，输出 ` ```python `，GitHub 上带高亮
- **表格单元格里的换行保留成 `<br>`**：单元格换行若输出 `\n`，外层为对齐单元格要压平空白，
  两行内容会被**吃掉换行粘成一行**（"第一行\n第二行" → "第一行第二行"），数据静默变形
- 链接 URL：空格与括号做百分号编码，否则 `a b.html` 断链、`p(1).html` 被提前截断
- 行内 SVG：**整块导出为 .svg 图片文件**，其内部 `<title>`/`<text>` 文本不会泄漏成正文乱码
- 图题/表题：`<figcaption>`、`<table><caption>` 转为紧邻的斜体说明行
- 引用块合并：题记 + 出处合并成同一个 `>` 引用块
- 样式识别：`font-style:italic` 转为 `*斜体*`

支持元素：标题 1-6、粗斜体删除线、行内/块级代码、有序无序（含嵌套）列表、引用、表格、图片（含内联 SVG）、链接、水平线、上下标、ruby 注音。

## 自检：转换完自动判断，不需要人工检查

**页面内置**：每本书转换完成时立即自动校验，结果直接显示在书目卡片上。
- 卡片顶部有一条汇总栏（`3 本有错误` / `全部无问题`），一眼看完，不用逐本点
- 每本书下面有自检面板：有错误时**自动展开**列出问题，措辞说明后果（如"未闭合的粗体会吞掉后面内容"）
- 手动编辑 Markdown 时会**防抖重跑**，面板显示的永远是当前内容的结论
- **有致命错误时阻止上传**，并明确告知原因；只是提醒的不拦

检查项（纯本地计算，不联网）：

| 级别 | 检查内容 |
| --- | --- |
| ❌ 错误 | 正文粗体标记未闭合、代码围栏未闭合（会把后面整章当代码）、代码块内 `#` 泄漏成标题、标题超过 H6、**图片指向不存在的文件**（仓库里会裂图） |
| ⚠️ 提醒 | 标题层级跳级、表格列数不齐、表格缺分隔行、行内代码未闭合、`<sub>/<sup>` 不成对 |

**粗体闭合性采用扫描而不是数奇偶**。真实书籽里 `**` 几乎满地都是——代码块里的幂运算
`a ** b`、行内代码的 `**options`、转义过的 `\*\*`、正文里的裸星号，都会影响计数。
如果按奇偶报错，一本含 36000+ 个 `**` 的书会被永远阻断上传。

现在的做法：先把非正文区（围栏代码块、行内代码、转义、HTML 标签、链接目标）
全部填空，再按 CommonMark 的 flanking 规则扫描配对。实测确认：
`a ** b ** c **` 整串原样输出（不是粗体），而 `前面**没关的粗体` 才真的会报错。

**命令行批量**（给开发/回归用）：

```bash
node check_markdown.js            # 扫描 samples/ 下全部 EPUB，一次跑完
node check_markdown.js diag       # 只跑指定样本
SHOW=1 node check_markdown.js     # 顺便打印生成的 Markdown
```

批量脚本除了跑页面内置的自检，还会用 **marked**（GitHub 同款 GFM 解析器）与 **commonmark**（官方规范）做双解析器交叉验证：

- **语法合法性**：标记是否成对、围栏是否成对、表格列数是否一致、标题有无跳级、链接有无未编码空格……与具体书无关，任何输出都必须满足
- **元素保真**：原书里有的元素（表格/删除线/图片/上下标…），输出里必须还在，且被解析成正确的节点而非退化成纯文本

全部通过退出码 0，可直接接入 CI。当前 8 个样本全部通过：
big 19/19、bold_noise 22/22、diag 30/30、dirty 23/23、full 29/29、md_check 38/38、sample 19/19、style_test 20/20。

**仓库首页的回归**（改过渲染就顺手跑一遍）：

```bash
node readme_check.js          # 假 GitHub 内存仓库，60 项断言
node make_readme_preview.js   # 生成 readme_preview.html，肉眼看清单效果
```

`readme_check.js` 把「有封面 / 无封面 / 仓库里还没有 books.json」三种情况一次摆开，验证
`books.json` 合并时不会吃掉别的书、表格每行都是 4 列（否则整张表错列）、中文路径没被整串
百分号编码。

假仓库刻意按真实 API 的脾气来：`PATCH` 只认复数 `/git/refs/heads/`，写单数 `ref` 直接 404；
blob sha 也按真实规则算（`sha1("blob <长度>\0" + 内容)`），不用自增编号糊弄。
它还会数「批量提交成功几次、退回逐文件上传几次」——逐文件上传是降级路径，正常一次都不该出现，
所以单独断言，不能靠"图片都到了"代表没退化（降级也能把图传上去，只是慢十倍）。

最后一段是**端到端**的：真跑一遍 `样本 dirty.epub → epubToMarkdown → uploadBook`，
再核对 markdown 里引用的每个 `images/xxx` 是不是都提交到了仓库同名路径。
差一个字符（空格、括号、大小写、扩展名）就是一张裂图 —— 这是"GitHub 上看不到图"的直接判据。

`make_readme_preview.js` 走的是页面里真实的 `updateReadme()`，只是把 GitHub
换成内存假仓库、封面换成内联 SVG，所以预览出来什么样，真上传后就是什么样。

> 该脚本需要三个 npm 包：`jsdom`（跑页面代码）、`marked`（GitHub 同款解析器）、`commonmark`（官方规范）。
> 用 `npm install jsdom marked commonmark` 安装到项目目录后运行即可。
> 工具本体 `book2md.html` 本身零依赖，单文件双击就能用。

| dirty（脏图名 + 脏格式） | 23/23 |

这套检查实际抓出过几个真问题（`dirty.epub` 这一本就直接暴露了 6 个：空书名、标题粘连、标题整体降级、空格/括号/井号图名裂图、井号图丢失、表格列被截断）：`<style>` 里的 CSS 类强调原本识别不到（`DOMParser` 产生的文档不属于浏览器窗口，`getComputedStyle` 对它返回空值，只能自己解析 `<style>` 规则做类名匹配）、代码块内的 `# 注释` 泄漏成真标题、`<sub>`/`<sup>` 被拉平。

## 上传速度

两项优化，都实测有效：

**1. 自适应并发上传（AIMD）** —— GitHub 的 blob 是内容寻址的（同样的内容永远得到同一个 sha），
不会移动分支引用，所以可以放心并发。

实测 300 个文件、每次往返 40ms：

| 并发 | 耗时 | 说明 |
| --- | --- | --- |
| 1 | 13229 ms | 串行基线 |
| 6 | 2201 ms | 旧版本固定值 |
| 12 | 1075 ms | 现在的起点 |
| 16 | 852 ms | 无限流时更快，但撞限流要重试 |
| 24 | 567 ms | 收益递减且容易触发限流 |

所以不做固定值，改成**自适应**：起点 12，连续成功就加一档（上限 24），
一旦收到 GitHub 的 403/429 二次限流，立刻**并发砍半 + 退避 2 秒 + 就地重试**。

实测同一本书：2302ms → **1394ms（8.6 倍于串行）**；
模拟限流时并发自动降到 7，文件仍全部提交成功。

**2. 跳过内容未变的文件** —— 上传前在本地算出文件的 git blob SHA-1，
和仓库里已有的 SHA-1 比对，相同就说明那个 blob 已经在 GitHub 上了，**一个字节都不用传**。

重复上传同一本书、或微调正文后重传时效果最明显：图片全部跳过，只传改动过的文件。
实测改 5 / 60 个文件 → 只重传 5 个（**重传量降到 1/12**）。

SHA-1 是纯 JS 实现（不依赖 WebCrypto 的异步接口），已用 Node 原生 crypto
对 9 组数据交叉验证过（含 55/56/57 字节的分组边界），性能约 2.3ms / 100KB，可以忽略不计。

> 顺带说明：曾评估过用 Git Trees API 的 `content` 字段一次传多个文件（能省掉全部 blob 请求），
> 但该字段只接受 UTF-8 文本，**图片会被损坏**，故未采用。

## 刷新页面草稿不丢

以前刷新一下页面 = 全部重来：书要重新拖进来、重新转换，改过的正文和文件夹名全没。
现在每本书都会存进浏览器本地的 IndexedDB，**刷新、关标签页、明天再打开都还在**。

| 存了什么 | 说明 |
| --- | --- |
| 正文（Markdown） | 包括在编辑框里改过的每一个字 |
| 配图 + 原 EPUB/PDF 文件 | 恢复后能直接重新转换、直接上传，不只是"能看" |
| 文件夹名、勾选状态 | 仓库里放哪儿、要不要保留原件 |
| 自检结果 | 打开就能看到上次那本书有没有问题 |

打开页面时会自动恢复，并在日志里写清「已恢复上次未完成的 N 本书（存于 X 分钟前）」。
点「清空」会连草稿一起删掉 —— 这是唯一主动丢弃的入口。

三个坑，都在实现里躲开了：

| 坑 | 后果 | 做法 |
| --- | --- | --- |
| 删掉的书没从库里删 | 刷新后自己回来了，怎么删都删不掉 | 每次保存时对比存活 id，多余的记录显式 `delete` |
| 每敲一个字都重写配图 | 一本 300 图的书打字会卡死 | 文本和二进制分开存，改正文只写文本那条 |
| 页面刚打开就先"清空" | 越刷新越干净，等于没存 | 只有本次会话确实写过，才允许清空 |

配图太大存不下时会降级：正文照样恢复，只是那本书需要重新拖一次原文件才能重新转换 ——
日志会明说，不会让人对着一本"能看不能传"的书猜。

## 管理仓库里已有的书

点「**管理仓库书籍**」会读出仓库里现有的书，每本一行，可以**改名**和**删除**。
这两个操作以前只能上 GitHub 网页一页页点，或者本地改个名字重传一本（旧的还留在仓库里占位）。

**改名**走的是 Git Trees API 的"按 sha 引用已有 blob"：把同一批 blob 的 sha 挂到新路径上，
再把旧路径删掉。所以**整本书改名是一个 commit、零字节上传** ——
300 张图的书也不需要重传任何内容。主文件（`xx.md` / `xx.epub` / `xx.pdf`）跟着书名改名，
封面和 `images/` 下的配图保持原样搬过去，`books.json` 里的键同步改掉（书名这类元数据不动）。

**删除**是在 tree 里把那些 path 的 `sha` 写成 `null`。

> 这里有个容易写错、错了还不报错的地方：tree 条目里**省略不写**等于没删 ——
> `base_tree` 会把未提及的路径原样带回来。所以必须显式写 `sha: null`。
> 这一条如果写错，页面会显示"已删除"而 GitHub 上一个字节都没变。
> 仓库里的删除不可撤销，点下去会先弹确认，说清要删几个文件。

两个操作完成后都会自动重建首页，否则 README 里会挂着已经删掉/改名的死链接。
改名撞车（目标目录已经有东西）会直接拦下来，不会静默覆盖。

## 说明

- Token 只存在本机浏览器，不上传第三方；上传时仅用于向 GitHub 认证。
- EPUB 转换全部在浏览器内存中完成，不产生临时文件。
- 超大 EPUB（含几百张图）处理较慢属正常，页面有进度条。

python make_full_epub.py       # samples/full.epub：多章节 + 图片 + 表格 + 嵌套列表

## 回归测试

```bash
node check_markdown.js    # 转换质量：10 本样本 + 真 commonmark 解析器对拍
node readme_check.js      # 上传与首页：假 GitHub（真 git blob sha），60 条
node ui_check.js          # 界面行为：只有界面动起来才暴露的问题，22 条
node repo_ops_check.js    # 仓库书籍改名/删除：假 GitHub，42 条
node draft_check.js       # 草稿暂存：内存版 IndexedDB，26 条
node repo_pages_check.js  # 仓库门面：.gitattributes + 书籍目录页死链，21 条
```

五套假环境都刻意"不惯着"页面代码：假 GitHub 会真算 git blob SHA-1、
只在 PATCH 成功后才移动分支头、单数 `/git/ref/` 一律 404、
tree 条目 `sha: null` 才真的删掉文件 ——
因为**假仓库比真仓库失真，测试就等于白写**（前几次栽在 PATCH 单复数、假 sha、
以及「省略条目 = 没删」上）。

其中 `repo_pages_check.js` 会**逐条解析目录页里的 Markdown 链接**，
按 GitHub 的规则（`x.md` 相对当前文件、`/x.md` 相对仓库根）解析成仓库内路径，
再确认目标文件真实存在。这样"目录页里挂了个指向不存在文件的链接"这种
只看日志一片绿、只有点开页面才 404 的错误，能当场被抓出来。
